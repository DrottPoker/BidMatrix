# Database migrations

BidMatrix stores ordered schema changes as embedded SQL files in `BidMatrix.Database`.

## Development

The API applies pending migrations during Development startup. Docker Compose creates a database owner role from `POSTGRES_USER` plus separate `bidmatrix_app`, `bidmatrix_audit`, and `bidmatrix_auth` runtime roles from `infra/postgres/init/001-create-application-role.sh`.

The API uses:

- `POSTGRES_USER` and `POSTGRES_PASSWORD` for Development migration execution.
- `POSTGRES_APP_USER` and `POSTGRES_APP_PASSWORD` for normal application connections.
- `POSTGRES_AUDIT_USER` and `POSTGRES_AUDIT_PASSWORD` for append-only audit operations.
- `POSTGRES_AUTH_USER` and `POSTGRES_AUTH_PASSWORD` for the isolated Better Auth schema.

The application role must not own the database and must not have `BYPASSRLS`.

`POSTGRES_MIGRATION_HOST` can select a direct database endpoint while `POSTGRES_HOST` selects a pooled runtime endpoint. Neon requires this separation because schema migrations must use the direct endpoint. Neon development connections use `POSTGRES_SSL_MODE=VerifyFull` and `POSTGRES_CHANNEL_BINDING=Require`.

Apply the migration chain without starting the application or Development seeder:

```powershell
$env:ASPNETCORE_ENVIRONMENT = 'Development'
dotnet run --project src/backend/BidMatrix.Api/BidMatrix.Api.csproj --configuration Release -- --migrate-database
dotnet run --project src/backend/BidMatrix.Api/BidMatrix.Api.csproj --configuration Release -- --verify-database-access
```

The first command uses only the migration role. The second proves independent application, audit, and auth connectivity plus the expected least-privilege role attributes and the auth role's isolation from BidMatrix user authority. Neon resource identifiers and branch discipline are documented in `docs/operations/neon-development.md`.

## Rollback strategy

Use forward-fix migrations. Do not rewrite already-applied migration files after they have been shared, because audit, policy, and approval records are security-sensitive. If a bad migration is applied, add a later migration that corrects the schema or seed data while preserving auditability.

## Non-Development

Automatic migration execution is disabled outside Development. Cloud deployment must run `--migrate-database` as a controlled release step with an owner or deployment role, run `--verify-database-access`, remove migration credentials from the runtime, and then run the API with the normal application role.

Migration `0010_s1_tenant_invitations` is historical. It added the invitation boundary later removed by migration `0016` under ADR 0018.

Migration `0011_s1_identity_controls` adds hash-only server sessions and account-recovery records with row-level security, idle and absolute session expiration, revocation state, and single-use recovery state. It revokes the application role's direct access to `user_credentials`, `user_sessions`, and `account_recovery_tokens`, then grants only narrow security-definer functions for authentication, session validation and revocation, password change, and recovery operations. Credential, session, recovery, and bootstrap mutations append token-free audit events.

Migration `0012_s1_federated_identities` adds explicit managed-provider mappings with row-level security. It stores provider name, issuer, verified email at link time, lifecycle state, and only the SHA-256 hash of issuer plus subject. The application role has no direct table access and can use only narrow functions to link from a validated session, resolve an existing mapping, list safe metadata, validate a session mapping, or revoke the mapping and all user sessions. Audit metadata excludes raw provider subjects and tokens.

Migration `0013_s1_managed_invitation_onboarding` is historical. Its managed invitation transaction is removed by migration `0016`.

Migration `0014_s1_better_auth` creates the separate `better_auth` schema and the 13 tables generated by the pinned Better Auth plugins. Its historical invitation-inspection grant is removed by migration `0016`. It never grants access to BidMatrix user, membership, role, application-session, or audit tables. Run `npm run auth:schema:check` whenever Better Auth packages or plugin configuration change.

Migration `0015_s1_simplified_authentication` implements ADR 0017. It fails
closed if any registered passkey exists, removes the unused passkey table and
passkey-only session field, and replaces the federated resolver and linker with
signatures that do not accept an authentication-method flag. The resulting
Better Auth schema has 12 tables until migration `0017` adds the rate-limit
table. BidMatrix role, explicit mapping, verified email, recent authentication,
session, and audit checks remain in force.

Migration `0016_s1_self_service_registration` implements ADR 0018. It refuses
to proceed while invitation rows exist, then removes the invitation table and
all invitation functions. It adds a narrow registration transaction that
creates a private organization, active user, disabled native credential, fixed
`owner` membership, federated identity mapping, and audit event. Only the
application role can execute it. The transaction cannot grant platform roles
or create agent work.

Migration `0017_s1_managed_identity_recovery` implements ADR 0019. It adds the
Better Auth database-backed rate-limit table and a fixed-search-path trigger on
managed credential password updates. The trigger matches only a hash-derived
federated mapping, rotates the BidMatrix security stamp, revokes active
application sessions and pending native recovery links, and appends token-free
audit evidence in the same transaction. The Better Auth role receives DML only
for its rate-limit table and cannot call the trigger function or read BidMatrix
authority tables directly. The resulting Better Auth schema has 13 tables.

The one-shot `--bootstrap-owner` command applies pending migrations through the configured migration role before creating the first platform owner. Outside Development, run it as a controlled release job and remove its migration and bootstrap credentials afterward. See `docs/operations/identity-bootstrap-and-recovery.md`.
